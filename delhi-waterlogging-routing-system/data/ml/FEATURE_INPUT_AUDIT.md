# Feature-input audit for the saved baseline model

**Scope:** Read-only inspection of the trained bundle, manifest, training script, dataset, and project source. This report does not add an inference endpoint and does not claim the model is ready for live users.

## Model and input contract

The saved artifact `ml/outputs/baseline_model.joblib` loaded successfully during inspection. It is a scikit-learn `Pipeline` with `SimpleImputer`, `StandardScaler`, and `LogisticRegression`, not an ONNX model. The fitted pipeline reports 18 inputs and the following ordered feature names, which match `feature_manifest.json`. Coefficients use `float64`; input values should be supplied as a numeric table/data frame with all 18 named columns and no invented substitutes. Continuous values should be finite numeric values; binary flags should be numeric 0/1. The imputer is part of the trained artifact, but that does not make missing geospatial sources available or justify arbitrary default values.

Positive class is 1. The bundle marks probabilities as not calibrated. It was smoke-tested on five rows already present in the CSV; this was not a test of coordinate-to-feature extraction.

## Evidence checked

- The manifest in `ml/outputs/feature_manifest.json` declares the ordered 18-feature input, excludes the two unverified history columns and target-derived `low_rain_positive`, and marks scores as uncalibrated.
- The loaded bundle’s fitted pipeline confirms `n_features_in_ == 18` and `feature_names_in_` exactly match the manifest. Its steps are imputation, scaling, and logistic regression; class labels are `[0, 1]`.
- `ml/train_baseline.py` derives only the two month encodings. The other 16 features are selected directly from the CSV.
- In the project tree, `backend/services/services/gis.py` is empty. The `data/` directory contains only the CSV. A project search found no DEM/DSM GeoTIFF, shapefile, GeoJSON, GeoPackage, or GIS feature-extraction implementation. The other backend service files are also empty.
- No source GIS layers or metadata document the derivation, coverage, date, projection, units, or null/cap conventions for the precomputed terrain and distance fields.

## Readiness and safe next step

At present, **none of the 16 terrain/mapped-feature inputs has a verified coordinate-to-feature implementation in this project**. The month features are computable only after a prediction date is defined. Therefore the saved bundle can be loaded and scores can be calculated for rows that already have the complete feature table, but it cannot yet be safely called with an arbitrary new latitude/longitude.

Do not use zero, a city-wide average, or a guessed distance as a replacement for a missing map/terrain value. The model’s imputer was trained as part of the pipeline, but silently passing missing GIS fields may still yield unsupported or misleading predictions; a future service should reject or explicitly mark a prediction unavailable when required source data is absent.

The smallest next implementation step is **a read-only GIS data feasibility/provenance spike, not an API**: obtain the original DEM and vector source layers (or their exact names, versions, licenses and preprocessing recipe), then define and test one deterministic function that takes `(latitude, longitude, prediction_date)` and produces the exact 18 named fields in the training contract. Validate its values against known rows in the CSV before considering a backend endpoint. If the original sources/recipe cannot be recovered, retraining against features that can be reliably generated at inference time will be necessary before live integration.
